# 1. Назначение и границы системы

## 1.1. Назначение

CineVault — веб-информационная система, помогающая пользователю организовывать личную фильмотеку и 
выбирать фильм для просмотра с учётом доступного времени, жанров, настроения, рейтинга и других предпочтений.

Система объединяет:
- каталог фильмов;
- подробные страницы фильмов;
- личную коллекцию пользователя;
- избранное;
- пользовательские оценки;
- историю просмотров;
- подбор фильма по параметрам;
- поиск и фильтрацию;
- профиль и персональную статистику;
- рекомендации, основанные на доступных данных и правилах ранжирования.

## 1.2. Целевая аудитория

Люди, которые смотрят фильмы дома, хотят вести собственную коллекцию и быстрее принимать решение о просмотре. Интерфейс должен быть понятен без инструкции.

## 1.3. Платформы

Адаптивное веб-приложение для настольных компьютеров, планшетов и мобильных устройств.

## 1.4. Роли

### Гость
Может:
- открывать главную страницу;
- просматривать каталог и карточки фильмов;
- искать и фильтровать фильмы;
- проходить подбор без сохранения персональных результатов;
- открывать страницу фильма.

Не может:
- сохранять личную фильмотеку на сервере;
- сохранять пользовательские оценки и историю между устройствами;
- просматривать персональные данные другого пользователя.

### Авторизованный пользователь
Может:
- выполнять все действия гостя;
- добавлять фильмы в личную коллекцию;
- менять статус фильма в коллекции;
- добавлять и удалять фильмы из избранного;
- ставить, изменять и удалять собственную оценку;
- сохранять историю просмотров;
- управлять собственными предпочтениями;
- получать персональные рекомендации, если для них достаточно данных.

### Администратор
В минимальной версии отдельный административный интерфейс не обязателен. Административное управление каталогом, жанрами и справочниками относится к следующему этапу, если оно будет включено в согласованные требования. Нельзя просто показать пользователю скрытые административные действия без серверной авторизации.

## 1.5. Что не входит в MVP

- потоковое воспроизведение фильмов;
- покупка или аренда фильмов;
- социальная сеть, подписки и комментарии;
- микросервисная архитектура;
- сложная рекомендательная модель, требующая отдельного обучения;
- автоматические уведомления;
- полноценная аналитическая панель администратора;
- реальные трейлеры и галерея, если нет надёжного источника данных и согласованного интерфейса.

# 2. Основные принципы проектирования

1. **Единый источник истины.** Состояние фильма для конкретного пользователя не должно независимо вычисляться на разных страницах.
2. **Разделение каталога и пользовательской коллекции.** Фильм — общая сущность каталога; статус, оценка и даты — пользовательские данные.
3. **Бизнес-логика отдельно от UI.** Компонент отображает состояние и вызывает действие; правила изменения данных не должны копироваться по страницам.
4. **Предсказуемость.** Одинаковое действие даёт одинаковый результат при одинаковом исходном состоянии.
5. **Объяснимый подбор.** Система не должна молча нарушать обязательные ограничения.
6. **Отсутствие фиктивной статистики.** Пользовательские счётчики строятся из пользовательских записей, а не из заранее заданных чисел.
7. **Обработка пустых состояний.** Отсутствие результатов — нормальный сценарий, а не повод показывать неподходящий фильм.
8. **Постепенная интеграция.** Сначала исправляется согласованность frontend-прототипа, затем согласуются API и схема БД, затем подключается backend.
9. **Сохранение текущего визуального направления.** Тёмная кинематографичная тема, бордовый акцент, крупные постеры, 
    горизонтальные ряды и верхняя навигация остаются базой. Не превращать интерфейс в dashboard.
10. **Доступность.** Клавиатурная навигация, видимый фокус, понятные подписи, доступные состояния кнопок и уважение к `prefers-reduced-motion`.

# 3. Карта страниц и назначение

Маршруты:
- `/` — главная;
- `/catalog` — каталог;
- `/movie/:id` — подробная страница фильма;
- `/picker` — подбор фильма;
- `/library` — личная фильмотека;
- `/favorites` — избранное;
- `/profile` — профиль;
- `*` — страница 404.

## 3.1. Общая оболочка

Общие элементы:
- шапка;
- главная навигация;
- поиск;
- меню профиля;
- контейнер страницы;
- подвал;
- системные уведомления, если они предусмотрены существующей архитектурой;
- переходы между страницами и декоративные эффекты.

Общие компоненты не должны содержать бизнес-логику конкретной страницы. Например, `MovieCard` может вызвать действие «добавить в избранное», 
    но само правило сохранения должно находиться в общем слое состояния/сервиса.

## 3.2. Главная `/`

### Назначение
Быстрый вход в каталог, подбор и личную коллекцию.

### Возможные секции
- крупный кинематографичный блок с выбранным фильмом;
- подбор по настроению;
- популярные/рекомендуемые фильмы;
- тематические подборки;
- недавно просмотренные фильмы — только если есть реальные данные истории;
- фильмы из личной коллекции — только если они действительно находятся в коллекции;
- переход к подборщику.

### Правила
- «Ваша фильмотека» показывает коллекцию, а не избранное.
- Если пользователь не авторизован или коллекция пуста, показать корректное пустое состояние и понятное действие.
- Счётчики и списки должны использовать один источник данных.
- Нельзя отображать фиктивные даты просмотра или персональные оценки как реальные.
- Блок «Популярные» должен опираться на определённое поле/правило сортировки. Если такого показателя нет, 
    блок переименовать в «Подборка CineVault» или использовать явно заданный демонстрационный порядок.

## 3.3. Каталог `/catalog`

### Назначение
Просмотр, поиск, фильтрация и сортировка каталога.

### Функции
- поиск по названию, оригинальному названию, режиссёру и жанрам;
- фильтр по жанрам;
- фильтр по диапазону лет;
- фильтр по минимальному рейтингу;
- фильтр по длительности;
- фильтр по стране, если страна действительно есть в данных;
- сортировка;
- сброс фильтров;
- открытие страницы фильма.

### Правила фильтрации
- Между разными группами фильтров применяется логика AND: фильм должен соответствовать всем активным группам.
- Если внутри жанров разрешено выбирать несколько значений, по умолчанию используется OR внутри группы: фильм подходит, если у него есть хотя бы один выбранный жанр. Это поведение нужно явно обозначить в интерфейсе.
- Пустое значение фильтра означает «не ограничивать по этому критерию».
- Границы диапазонов лет не должны пересекаться случайным образом.
- При изменении фильтров результаты обновляются сразу или после явно обозначенного действия «Применить» — не смешивать оба паттерна в одном интерфейсе.
- Кнопка сброса возвращает все фильтры и сортировку к значениям по умолчанию.
- Пустой результат показывает сообщение и действие сброса фильтров.
- Сортировка не должна лишь менять надпись: порядок элементов реально меняется.

### Согласованные диапазоны лет
Рекомендуемые непересекающиеся диапазоны:
- до 1999 включительно;
- 2000–2009;
- 2010–2014;
- 2015–2019;
- 2020 и позднее.

Если текущий интерфейс использует другие подписи, синхронизировать подписи и условия фильтра. Границы должны быть однозначны и проверяться тестами.

### Сортировка
Поддерживаемые варианты должны иметь реальную реализацию:
- по рейтингу — по убыванию численного рейтинга;
- по году — по убыванию или возрастанию согласно выбранному названию;
- по названию — алфавитно;
- популярные — только при наличии поля популярности или заранее определённого демонстрационного порядка. Не использовать название «Популярные» для исходного порядка массива.

## 3.4. Страница фильма `/movie/:id`

### Назначение
Предоставить полную доступную информацию о фильме и действия с ним.

### Данные
- название и оригинальное название;
- год;
- длительность;
- жанры;
- рейтинг внешнего источника, если он есть;
- постер и фон;
- режиссёр;
- описание;
- страна/страны, если данные доступны;
- актёрский состав и роли, если доступны;
- дополнительные изображения — только при наличии данных;
- пользовательская оценка текущего пользователя;
- статус фильма в личной коллекции;
- состояние избранного;
- похожие фильмы, если определён способ их выбора.

### Действия
- добавить в коллекцию;
- изменить статус коллекции;
- удалить из коллекции;
- добавить/убрать из избранного;
- поставить/изменить/удалить личную оценку;
- отметить просмотр;
- перейти к подбору или открыть похожий фильм.

### Правила
- Внешний рейтинг фильма и личная оценка пользователя — разные показатели, их нельзя смешивать.
- Если пользователь ещё не оценивал фильм, показывать нейтральное состояние, а не демонстрационную личную оценку.
- Если фильм не найден, показать страницу «Фильм не найден» с переходом в каталог.
- Если трейлер недоступен, не показывать кнопку, которая открывает фиктивный плеер. Допустимы скрытие действия или явно обозначенное состояние «Трейлер недоступен».
- Блок «Создатели» не должен заполняться повторением режиссёра, страны или других несвязанных полей.
- Недоступные сведения не заменять выдуманными значениями.
- Состояния кнопок синхронизированы с общей моделью коллекции.

## 3.5. Подбор `/picker`

Подбор — ключевой сценарий CineVault. Он состоит из двух независимых частей:
1. диалоговый пользовательский сценарий;
2. алгоритм фильтрации и ранжирования.

Интерфейс не должен содержать алгоритм ранжирования в виде большого набора JSX-условий. Алгоритм реализуется в отдельном модуле/сервисе и тестируется независимо.

Подробная логика приведена в разделе 7.

## 3.6. Личная фильмотека `/library`

### Назначение
Управление фильмами, которые пользователь добавил в свою коллекцию.

### Статусы коллекции
Для MVP использовать ограниченный набор:
- `planned` — планирую посмотреть;
- `watching` — смотрю/просматриваю;
- `watched` — просмотрено.

Статус `dropped` («бросил просмотр») можно добавить позднее, если он действительно нужен интерфейсу. Не добавлять статусы только ради полноты модели.

Избранное не является статусом коллекции: это отдельный признак/связь.

### Функции
- просмотр всех фильмов коллекции;
- фильтрация по статусу;
- сортировка;
- изменение статуса;
- удаление из коллекции;
- переход к странице фильма;
- отображение пустого состояния.

### Правила
- Фильм находится в коллекции, если существует связь пользователя с фильмом.
- Фильм может быть в избранном и не находиться в коллекции, если продукт специально не решит иначе.
- Удаление из коллекции не должно автоматически удалять избранное или историю просмотров.
- Если пользователь отмечает фильм как просмотренный, запись истории создаётся по правилам раздела 5.
- Все секции, счётчики и вкладки вычисляются из одной модели данных.
- Вкладка «Смотрю» содержит только записи со статусом `watching`.
- Нельзя показывать фильм в разделе «Смотрю» лишь потому, что он есть в моковом массиве с не связанным с пользователем статусом.

## 3.7. Избранное `/favorites`

### Назначение
Быстрый доступ к фильмам, которые пользователь отметил как избранные.

### Правила
- Избранное — самостоятельный список/связь, а не псевдоним личной коллекции.
- Добавление/удаление синхронно отображается на главной, странице фильма, в каталоге и в профиле, если там есть соответствующий элемент.
- Повторное добавление не создаёт дубликат.
- Удаление из избранного не удаляет фильм из коллекции и не удаляет историю.
- Пустое состояние предлагает перейти в каталог.

## 3.8. Профиль `/profile`

### Назначение
Показывать реальные персональные данные и настройки.

### Минимальные блоки
- краткая статистика коллекции;
- количество просмотренных фильмов;
- список недавних просмотров;
- личные оценки;
- избранное/планируемые фильмы при необходимости;
- настройки интерфейса, только если они действительно работают.

### Правила
- Количество фильмов в коллекции = число уникальных связей пользователя с фильмами.
- Количество просмотренных фильмов = число уникальных фильмов с завершённым просмотром или статусом `watched` — выбрать одно правило и использовать везде. Для MVP рекомендуется считать уникальные фильмы со статусом `watched`, а историю событий хранить отдельно.
- Средняя личная оценка = среднее арифметическое только по существующим пользовательским оценкам текущего пользователя. Не учитывать внешний рейтинг и демонстрационные оценки.
- История просмотров содержит реальные события и даты. Если событий нет, показывать пустое состояние.
- Переключатель настройки должен изменять реальное поведение и сохраняться. Если функция не реализована, не выдавать декоративный переключатель за работающую настройку.
- Пользователь не должен видеть персональные данные другого пользователя.

## 3.9. Поиск в шапке

### Поиск по
- названию;
- оригинальному названию;
- режиссёру;
- жанру.

Поиск в шапке и в каталоге должен использовать общий модуль нормализации и сопоставления текста, чтобы одинаковый запрос не давал противоречивые результаты.

### Поведение
- игнорировать регистр;
- корректно обрабатывать пробелы в начале и конце;
- не падать на пустом запросе;
- клавиатурная навигация по подсказкам;
- `Enter` открывает выбранный результат либо страницу каталога с запросом;
- `Escape` закрывает подсказки;
- при отсутствии результатов показывать понятное сообщение;
- выбирать безопасное поведение при слишком коротком запросе, чтобы не отображать весь каталог в подсказках.

## 3.10. Страница 404

- сообщить, что страница не найдена;
- дать переход на главную и в каталог;
- не показывать пустой экран;
- не маскировать ошибку маршрута под ошибку загрузки фильма.

# 4. Единая модель состояния пользователя

## 4.1. Базовый принцип

Каталог содержит сведения о фильме. Пользовательские действия хранятся отдельно. Нельзя хранить разные независимые копии одного статуса на странице фильма, в библиотеке и профиле.

## 4.2. Рекомендуемые сущности

### Movie
Общие данные каталога:
- `id` — внутренний идентификатор;
- `tmdbId` — необязательный внешний идентификатор;
- `title`;
- `originalTitle`;
- `year`;
- `durationMinutes`;
- `genres`;
- `externalRating`;
- `posterUrl`;
- `backdropUrl`;
- `director`;
- `description`;
- `countries`;
- `cast` — при наличии;
- `popularity` — только если показатель реально доступен;
- `createdAt`, `updatedAt` — если необходимы на сервере.

В интерфейсе можно временно использовать моковые записи. Не привязывать все внутренние ссылки исключительно к заголовку фильма: названия могут повторяться.

### UserMovie
Связь пользователя с фильмом:
- `userId`;
- `movieId`;
- `status`: `planned | watching | watched`;
- `personalRating`: число в согласованном диапазоне либо `null`;
- `addedAt`;
- `statusUpdatedAt`;
- `watchedAt` — дата последнего/завершённого просмотра, если применимо.

Уникальность: одна запись на пару `(userId, movieId)` в рамках текущего простого сценария.

### Favorite
Связь пользователя с избранным фильмом:
- `userId`;
- `movieId`;
- `createdAt`.

Уникальность пары `(userId, movieId)`.

### WatchHistory
Событие просмотра:
- `id`;
- `userId`;
- `movieId`;
- `watchedAt`;
- необязательная заметка/источник, если это понадобится.

История событий и текущий статус — разные понятия. Один фильм можно пересмотреть несколько раз, поэтому история может содержать несколько событий, а `UserMovie` остаётся одной записью.

### UserPreferences
Предпочтения для персонализации:
- предпочитаемые жанры;
- исключаемые жанры, если пользователь явно выбирает их;
- предпочитаемые длительности;
- минимальный рейтинг;
- другие критерии только после определения их смысла.

В MVP предпочтения подборщика можно хранить в состоянии текущего диалога, а сохранённые постоянные предпочтения добавить отдельно. Не смешивать ответы одного разового подбора с постоянными настройками пользователя.

## 4.3. Внешний рейтинг и личная оценка

Обязательное разделение:
- `externalRating` — рейтинг из каталога/внешнего источника;
- `personalRating` — оценка, поставленная текущим пользователем.

В UI они должны иметь разные подписи. Личная оценка не может автоматически заполняться рейтингом TMDB или моковым рейтингом.

## 4.4. Производные показатели

Счётчики не хранить отдельно, если их можно надёжно вычислить из записей. Если в будущем счётчики кэшируются на сервере, источник истины всё равно остаётся в основных сущностях.

Примеры:
- `libraryCount` = количество уникальных `UserMovie`;
- `favoriteCount` = количество уникальных `Favorite`;
- `watchedCount` = количество уникальных `UserMovie` со статусом `watched`;
- `averagePersonalRating` = среднее по непустым `personalRating`.

Нельзя увеличивать статическое число на единицу при нажатии: нужно пересчитать результат из состояния.

# 5. Правила переходов состояния

## 5.1. Добавление фильма в коллекцию

Если фильма ещё нет в коллекции:
- создать связь `UserMovie`;
- начальный статус по умолчанию — `planned`;
- личная оценка — `null`;
- зафиксировать `addedAt`.

Если запись уже есть:
- не создавать дубликат;
- сохранить текущий статус и оценку;
- UI должен показать, что фильм уже в коллекции, или предложить изменить статус.

## 5.2. Изменение статуса

- `planned → watching`: обновить статус и `statusUpdatedAt`.
- `planned → watched`: обновить статус, дату просмотра при её наличии и создать событие истории согласно согласованному UX.
- `watching → watched`: завершить просмотр и создать событие истории.
- `watched → planned`: изменить текущий статус; уже сохранённое событие истории не удалять автоматически.
- `watched → watching`: разрешить только через явное действие пользователя; прежняя история остаётся.
- повторное назначение того же статуса не должно создавать дубликаты событий или лишние записи.

### Правило для истории
Для MVP при явном действии «Отметить просмотренным» создаётся одно событие просмотра. При простом повторном нажатии на уже активный статус событие не создаётся. Отдельное действие «Посмотрел ещё раз» можно добавить позже, если интерфейс будет его поддерживать.

## 5.3. Оценка

- Пользователь может поставить оценку только в определённом интерфейсом диапазоне. Рекомендуемый диапазон — 1–10 с шагом 1; если текущий UI использует иной диапазон, выбрать один и унифицировать.
- Оценка хранится отдельно от внешнего рейтинга.
- Повторная оценка обновляет существующее значение, а не создаёт новую запись.
- Удаление оценки переводит `personalRating` в `null`.
- Средний балл профиля пересчитывается из всех личных оценок.
- Если оценка связана только с записью коллекции, пользователь сначала должен добавить фильм в коллекцию; если продукт допускает оценку без добавления, это решение следует отразить в модели. Для MVP рекомендуется разрешить личную оценку только при существующей связи `UserMovie`, чтобы не создавать две конкурирующие модели оценок.

## 5.4. Избранное

- Добавление создаёт уникальную связь `Favorite`.
- Повторное добавление идемпотентно.
- Удаление убирает только связь `Favorite`.
- Изменение избранного не меняет статус коллекции и историю.

## 5.5. Удаление из коллекции

- Удаляется `UserMovie`.
- `Favorite` сохраняется.
- `WatchHistory` сохраняется.
- В личной статистике пересчитываются значения, основанные именно на коллекции.
- Если пользователь удаляет фильм со статусом `watched`, история просмотра не должна исчезать.
- Если оценки разрешены только в коллекции, удаление коллекции удаляет текущую личную оценку вместе с `UserMovie`, но не историю. Перед реализацией проверить, что UI явно отражает это правило.

## 5.6. Сохранение и восстановление состояния

В прототипе состояние может храниться в `localStorage`. Требования:
- безопасно обрабатывать отсутствие данных;
- обрабатывать некорректный JSON;
- проверять структуру данных после JSON.parse;
- использовать версионирование формата, если структура меняется;
- при несовместимых данных восстанавливаться к безопасному состоянию и не ломать приложение;
- все страницы читать данные из единого provider/store/service;
- не дублировать собственные реализации сохранения в каждом компоненте.

В целевой версии после появления backend пользовательские данные хранятся на сервере. `localStorage` может оставаться для UI-настроек или кэша, но не должен становиться вторым конфликтующим источником истины для пользовательской библиотеки.

# 6. Правила согласованности между страницами

Любое действие с фильмом должно немедленно отражаться во всех видимых местах, которые используют то же состояние.

| Действие | Страница фильма | Каталог/главная | Фильмотека | Избранное | Профиль |
|---|---|---|---|---|---|
| Добавить в коллекцию | обновить кнопку/статус | обновить доступные индикаторы | добавить фильм | без изменения | пересчитать счётчик |
| Изменить статус | показать новый статус | обновить пользовательский индикатор, если он есть | переместить в соответствующий раздел | без изменения | пересчитать статистику |
| Оценить фильм | показать личную оценку | показывать её только там, где явно предусмотрено | показать оценку при необходимости | без изменения | пересчитать среднее |
| Добавить в избранное | обновить кнопку | обновить индикатор | без изменения | добавить фильм | пересчитать избранное, если есть счётчик |
| Удалить из избранного | обновить кнопку | обновить индикатор | без изменения | удалить фильм | пересчитать избранное |
| Удалить из коллекции | обновить статус коллекции | убрать из блока личной коллекции | удалить | сохранить избранное | пересчитать коллекцию |

Ключевой критерий: страницы не должны самостоятельно хранить копии статуса фильма, которые расходятся между собой.

# 7. Подбор фильма: диалог, ограничения и алгоритм

## 7.1. Цель

Подобрать один или несколько фильмов, которые соответствуют условиям конкретного вечера. Алгоритм должен быть детерминированным и объяснимым: при одинаковых данных и параметрах он должен давать предсказуемый результат.

Для первой версии не требуется машинное обучение. Используется фильтрация и многофакторное ранжирование с явно заданными весами.

## 7.2. Разделение условий

### Жёсткие ограничения
Их нельзя нарушать молча:
- максимальная длительность, если пользователь обозначил её как обязательную;
- исключённые жанры;
- исключённые конкретные фильмы;
- иные явно помеченные пользователем как обязательные условия.

Если по жёстким условиям ничего не найдено, система должна сообщить об отсутствии совпадений и предложить изменить условия. Она не имеет права показывать неподходящий фильм как точное совпадение.

### Мягкие предпочтения
Их можно использовать для ранжирования:
- любимые жанры;
- настроение;
- желаемый период;
- желаемый рейтинг;
- предпочтения по длительности, если пользователь выбрал их как ориентир, а не жёсткое ограничение;
- дополнительные пожелания.

Интерфейс должен различать жёсткое ограничение и предпочтение. Если для конкретного критерия не нужен такой выбор, зафиксировать его семантику заранее.

## 7.3. Рекомендуемый диалог

Граф диалога нужен, потому что подбор состоит из последовательных шагов, имеет ветвления, возврат назад, пропуск необязательных вопросов и экран отсутствия совпадений. Граф фиксирует не внешний дизайн, а логику переходов.

### Шаг 1. Жанры
Вопрос: «Что хочется посмотреть?»
- можно выбрать один или несколько жанров;
- можно выбрать «Без предпочтений»;
- если жанры выбраны, они влияют на релевантность результата;
- выбор нескольких жанров означает совпадение хотя бы с одним выбранным жанром, если пользователь не выбрал строгий режим.

### Шаг 2. Настроение
Вопрос: «Какое настроение у вечера?»
- выбрать один или несколько поддерживаемых вариантов;
- настроение — предпочтение, а не обязательная характеристика, если оно явно не помечено как ограничение;
- каждое настроение должно быть связано с определёнными жанрами/тегами или иными данными. Не приписывать настроение фильму без правила сопоставления;
- если данных о настроении у фильмов нет, не делать вид, что алгоритм точно учитывает его. Для MVP использовать прозрачную таблицу соответствия жанров/тегов или убрать настроение из оценки до появления данных.

### Шаг 3. Время
Вопрос: «Сколько времени есть на фильм?»
- предложить ясные варианты длительности;
- определить, означает ли выбор максимум или ориентир;
- для MVP рекомендуем считать выбранное время максимальной длительностью, если пользователь выбирает вариант вроде «до 2 часов»;
- фильм, превышающий обязательный максимум, не должен попасть в точные результаты.

### Шаг 4. Период
Вопрос: «Какую эпоху предпочитаешь?»
- варианты соответствуют непересекающимся диапазонам лет;
- «Неважно» снимает ограничение;
- если период выбран как мягкое предпочтение, фильмы вне диапазона могут остаться в выдаче с меньшим баллом; если выбран как строгий фильтр, исключаются.

### Шаг 5. Рейтинг
Вопрос: «Насколько важен высокий рейтинг?»
- минимальный порог должен быть явно обозначен как строгий фильтр, если фильм ниже порога не допускается;
- альтернатива — выбрать «Рейтинг неважен»;
- нельзя незаметно игнорировать выбранный порог при поиске результата.

### Шаг 6. Дополнительные пожелания
Вопрос: «Что ещё важно?»
Возможные условия — только если данные позволяют проверить их:
- исключить выбранные жанры;
- исключить уже просмотренные фильмы;
- исключить фильмы из коллекции;
- исключить избранное/уже предложенные в этой сессии;
- прочие поддерживаемые признаки.

Не показывать пользователю опции, которые алгоритм не способен реализовать. Можно пропустить шаг.

### Результат
Показывать:
- фильм/список фильмов;
- постер и основные характеристики;
- объяснение соответствия выбранным предпочтениям;
- явные сведения о нарушенных/ослабленных мягких предпочтениях, если они есть;
- кнопки «Другой вариант», «Изменить условия», «Добавить в коллекцию», «Избранное», «Открыть фильм».

## 7.4. Граф диалога

```mermaid
flowchart TD
    A[Открыть подбор] --> B[Шаг 1: жанры]
    B --> C[Шаг 2: настроение]
    C --> D[Шаг 3: длительность]
    D --> E[Шаг 4: период]
    E --> F[Шаг 5: рейтинг]
    F --> G[Шаг 6: дополнительные пожелания]
    G --> H[Проверить параметры]
    H --> I[Фильтрация по жёстким ограничениям]
    I --> J{Есть кандидаты?}
    J -- Да --> K[Ранжирование по мягким предпочтениям]
    K --> L[Экран результата]
    L --> M{Действие пользователя}
    M -- Другой вариант --> N[Выбрать ещё не показанного кандидата]
    N --> L
    M -- Изменить условия --> B
    M -- Открыть фильм --> O[Страница фильма]
    M -- Добавить в коллекцию --> P[Обновить пользовательское состояние]
    J -- Нет --> Q[Нет точных совпадений]
    Q --> R[Предложить ослабить мягкие условия]
    R --> S{Пользователь согласен?}
    S -- Да --> T[Показать изменения условий]
    T --> K
    S -- Нет --> B
```

### Правила переходов
- «Назад» возвращает к предыдущему шагу, сохраняя уже выбранные ответы.
- «Продолжить» не теряет выбранные значения.
- Изменение ответа на шаге сбрасывает устаревший результат подбора.
- Результат не должен оставаться визуально действующим, если параметры уже изменились.
- Если пользователь меняет параметры после результата, требуется повторный запуск подбора.
- Необязательные шаги можно пропускать.
- Прогресс должен корректно учитывать выбранную последовательность шагов.
- Не показывать одновременно все вопросы, если реализуется диалоговый вариант.
- На мобильном экране один шаг должен быть понятен без чрезмерной прокрутки.

## 7.5. Алгоритм подбора

### Вход
Нормализованный объект параметров, например:

```ts
type PickerCriteria = {
  genres: string[];
  mood?: string;
  maxDurationMinutes?: number;
  preferredYearRange?: { from: number; to: number };
  minimumRating?: number;
  excludedGenres: string[];
  excludeWatched: boolean;
  excludeLibrary: boolean;
  excludeFavorites: boolean;
  excludedMovieIds: string[];
};
```

Типы могут быть адаптированы к существующему проекту, но семантика должна остаться явной. Не все поля обязательно нужны в первом интерфейсе; не добавлять поле, если для него нет реализации.

### Этап A. Валидация
- нормализовать пустые значения;
- проверить диапазоны годов;
- проверить длительность и рейтинг;
- удалить дубликаты из списков;
- проверить, что идентификаторы имеют ожидаемый тип;
- не допускать NaN/невалидные числа.

### Этап B. Жёсткая фильтрация
Для каждого фильма проверить:
1. фильм имеет необходимые данные для проверки условия;
2. не нарушает исключённые жанры;
3. не входит в список исключённых ID;
4. не превышает жёсткий лимит длительности;
5. удовлетворяет жёсткому порогу рейтинга, если выбран такой режим;
6. не просмотрен/не в коллекции/не в избранном, если пользователь включил соответствующие исключения.

Если данных для критерия нет, правило должно быть определено явно. Для жёсткого ограничения безопаснее не считать неизвестное значение соответствием; для мягкого предпочтения неизвестное значение получает нейтральный/нулевой вклад.

### Этап C. Расчёт балла
Пример стартовой схемы весов для мягких предпочтений:
- совпадение жанра — 40%;
- совпадение настроения — 20%;
- попадание в предпочитаемый период — 15%;
- рейтинг — 15%;
- близость длительности к предпочтительной — 10%.

Это стартовые веса для прототипа, а не научно доказанные константы. Их следует вынести в отдельную конфигурацию, документировать и проверять на тестовых сценариях.

Для каждого критерия вычисляется нормированный вклад в диапазоне `0..1`. Итоговый балл:
`score = Σ(weight_i × match_i) / Σ(active_weights) × 100`

Учитывать только критерии, для которых пользователь действительно задал предпочтение и которые можно оценить по имеющимся данным. Если предпочтение не задано, оно не должно снижать балл всех фильмов.

Пример:
- жанр совпал: `1.0`;
- настроение совпало по заранее определённой таблице: `1.0`;
- год в желаемом диапазоне: `1.0`;
- рейтинг соответствует предпочтению: `0.8`;
- длительность близка к выбранной: `0.7`.

Не использовать неподтверждённые поля и не выдумывать значения популярности/настроения.

### Этап D. Сортировка
Сортировать по:
1. итоговому баллу по убыванию;
2. затем по внешнему рейтингу по убыванию, если он доступен;
3. затем по стабильному ID для детерминированного порядка.

### Этап E. Объяснение результата
Формировать объяснение из реальных совпадений, например:
- «Подходит по выбранным жанрам: фантастика и триллер»;
- «Длительность — 118 минут, в пределах выбранного лимита»;
- «Рейтинг выше установленного минимума».

Не генерировать объяснение для критерия, который не проверялся. Не заявлять, что фильм подходит по настроению, если нет связи между настроением и данными фильма.

## 7.6. Отсутствие совпадений

Запрещено автоматически возвращать произвольный фильм, нарушающий жёсткие условия.

Вместо этого:
1. показать «По заданным обязательным условиям ничего не найдено»;
2. указать, какие условия ограничили выдачу;
3. предложить изменить конкретные мягкие предпочтения;
4. отдельно запросить согласие на изменение жёсткого ограничения;
5. повторить поиск только после согласованного изменения;
6. показать, какие условия были ослаблены.

Нельзя автоматически ослаблять рейтинг, жанры и длительность без сообщения пользователю. Нельзя нарушать явно исключённые жанры/фильмы, если пользователь не изменил соответствующие условия.

## 7.7. Кнопка «Другой вариант»

- Использовать уже отсортированный список кандидатов.
- В пределах одной сессии подбора не показывать повторно уже показанные фильмы, пока есть непоказанные кандидаты.
- Когда кандидаты закончились, сообщить об этом и предложить изменить параметры или начать заново.
- Не выбирать случайный фильм из всего каталога.
- Смена результата не должна изменять библиотеку/избранное автоматически.
- Повторный результат должен сохранять объяснение, соответствующее конкретному фильму.

## 7.8. Тестовые сценарии алгоритма
1. Нет критериев — выдача детерминирована, список не падает и не содержит дубликатов.
2. Выбран максимальный лимит — ни один точный результат не длиннее лимита.
3. Выбран исключённый жанр — фильм с этим жанром отсутствует.
4. Нет точных совпадений — экран пустого результата, а не случайный фильм.
5. Изменён критерий — старый результат больше не выдаётся как актуальный.
6. «Другой вариант» — не повторяет фильм, пока есть другие кандидаты.
7. Неизвестен рейтинг — он не проходит строгий минимальный порог.
8. Не задан жанр — жанровый критерий не влияет на итоговый балл.
9. Настроение не связано с данными фильма — нельзя начислять выдуманное совпадение.
10. Исключение просмотренных фильмов работает по единому источнику статусов.

# 8. Архитектура приложения

## 8.1. Целевая схема

```mermaid
flowchart LR
    U[Пользователь] --> FE[React + TypeScript]
    FE --> API[FastAPI REST API]
    API --> BL[Сервисы бизнес-логики]
    BL --> DB[(PostgreSQL)]
    BL --> TMDB[TMDB API]
    BL -. опционально .-> REDIS[(Redis)]
```

Redis — необязательный компонент. Не подключать его только потому, что он указан в предварительном стеке. Для MVP можно начать без кэша, пока не появится измеримая необходимость.

## 8.2. Frontend

Ответственность:
- отображение страниц;
- навигация;
- ввод параметров;
- отображение loading/error/empty/success состояний;
- локальные интерактивные состояния UI;
- вызов API;
- отображение полученных данных.

Frontend не должен быть единственным местом реализации критически важной бизнес-логики. Алгоритм подбора должен быть реализован и проверен в бизнес-слое, а на этапе прототипа может иметь временную клиентскую реализацию с тем же контрактом.

## 8.3. Backend

Ответственность:
- API;
- валидация входных данных;
- авторизация и проверка прав;
- бизнес-правила коллекции, оценок и истории;
- алгоритм подбора;
- чтение и запись в БД;
- интеграция с TMDB;
- обработка ошибок и преобразование их в понятные HTTP-ответы.

## 8.4. PostgreSQL

Хранит:
- каталог и справочники, если система сохраняет локальную копию данных;
- пользователей;
- пользовательскую коллекцию;
- избранное;
- историю;
- предпочтения.

Нужно определить, какие данные фильма хранятся в локальной БД, а какие запрашиваются извне. Для устойчивой работы рекомендуется сохранять минимально необходимые нормализованные данные фильма и внешний `tmdbId`, а обновление внешних данных реализовать отдельным сервисом.

## 8.5. TMDB API

- Все запросы к TMDB выполнять через backend, чтобы не раскрывать секретные ключи в клиентском коде.
- Проверять ошибки, лимиты и недоступность сервиса.
- Не считать внешний сервис единственным источником пользовательских данных.
- Отделять идентификатор TMDB от внутреннего ID.
- Не ломать страницу фильма, если дополнительная информация временно недоступна.
- Соблюдать условия использования и требования к атрибуции TMDB.

## 8.6. Рекомендуемая организация backend

Простая структура, без микросервисов:

```text
backend/
  app/
    main.py
    api/
      routes/
        movies.py
        library.py
        favorites.py
        ratings.py
        history.py
        picker.py
        auth.py
    core/
      config.py
      errors.py
    schemas/
      movie.py
      library.py
      picker.py
      user.py
    models/
      movie.py
      user.py
      user_movie.py
      favorite.py
      watch_history.py
    services/
      movie_service.py
      library_service.py
      picker_service.py
      tmdb_service.py
    repositories/
      movie_repository.py
      library_repository.py
    db/
      session.py
      base.py
    tests/
```

Это целевой ориентир, а не требование создать все файлы пустыми. Добавлять слои только там, где они дают ясное разделение ответственности.

# 9. Предварительная модель данных

## 9.1. Связи

```mermaid
erDiagram
    USER ||--o{ USER_MOVIE : owns
    MOVIE ||--o{ USER_MOVIE : appears_in
    USER ||--o{ FAVORITE : marks
    MOVIE ||--o{ FAVORITE : is_favorited
    USER ||--o{ WATCH_HISTORY : creates
    MOVIE ||--o{ WATCH_HISTORY : is_watched
    USER ||--o{ USER_PREFERENCE : configures
```

## 9.2. Ограничения целостности

- внутренние ID — стабильные идентификаторы, не названия;
- уникальная пара `(user_id, movie_id)` для `user_movie`;
- уникальная пара `(user_id, movie_id)` для `favorite`;
- внешний рейтинг не записывается в поле личной оценки;
- рейтинг ограничен согласованным диапазоном;
- статус ограничен перечислением разрешённых значений;
- внешние ключи защищают от осиротевших связей;
- удаление фильма из пользовательской коллекции не должно случайно удалять историю;
- поведение физического удаления фильма из каталога определить отдельно; обычно предпочтительнее не удалять фильм, пока на него ссылаются пользовательские записи.

## 9.3. Вопросы, которые нужно решить перед миграциями

1. Нужна ли регистрация/авторизация в первой версии или пока допустим один локальный демонстрационный пользователь?
2. Должна ли личная оценка требовать добавления фильма в коллекцию?
3. Храним ли страну, актёров и жанры нормализованными справочниками или достаточно полей/связей упрощённой модели для MVP?
4. Должна ли история хранить каждый просмотр или только последнюю дату? Рекомендуется отдельная таблица событий.
5. Как именно удаление пользовательского аккаунта влияет на персональные данные?

До согласования этих вопросов Copilot не должен самостоятельно создавать окончательную схему БД.

# 10. Предварительный REST API-контракт

API ниже — предложение для согласования. Его можно уточнить до реализации, но frontend и backend должны использовать один контракт.

## 10.1. Фильмы

- `GET /api/movies` — каталог с query-параметрами поиска, фильтров, сортировки и пагинации.
- `GET /api/movies/{movie_id}` — подробности фильма.
- `GET /api/movies/{movie_id}/similar` — похожие фильмы, если логика согласована.

Пример параметров каталога:
- `q`;
- `genre`;
- `year_from`;
- `year_to`;
- `min_rating`;
- `max_duration`;
- `country`;
- `sort`;
- `page`;
- `page_size`.

Нельзя принимать произвольную строку сортировки и подставлять её напрямую в SQL.

## 10.2. Личная коллекция

- `GET /api/library` — список коллекции текущего пользователя.
- `POST /api/library` — добавить фильм.
- `PATCH /api/library/{movie_id}` — изменить статус.
- `DELETE /api/library/{movie_id}` — удалить из коллекции.

Сервер обязан получать пользователя из контекста аутентификации, а не доверять произвольному `user_id` из тела запроса.

## 10.3. Избранное

- `GET /api/favorites`;
- `PUT /api/favorites/{movie_id}` — обеспечить наличие в избранном;
- `DELETE /api/favorites/{movie_id}` — удалить из избранного.

`PUT` выбран для идемпотентного добавления.

## 10.4. Оценки

- `PUT /api/movies/{movie_id}/rating` — создать или заменить личную оценку;
- `DELETE /api/movies/{movie_id}/rating` — удалить личную оценку.

Тело запроса содержит только оценку, а пользователь определяется по токену/сессии. Проверять диапазон на сервере.

## 10.5. История

- `GET /api/history`;
- `POST /api/history` — зарегистрировать просмотр;
- `DELETE /api/history/{history_id}` — удаление события, если это предусмотрено UX.

Повторный просмотр — отдельное событие. Автоматическое повторное создание события при каждом рендере запрещено.

## 10.6. Подбор

- `POST /api/picker/recommendations` — передать критерии и получить ранжированные результаты;
- опционально: `POST /api/picker/explain` не нужен, если объяснение возвращается в результате основного endpoint.

Пример концептуального ответа:

```json
{
  "items": [
    {
      "movieId": "movie-123",
      "score": 87.5,
      "reasons": [
        "Совпадает выбранный жанр",
        "Длительность не превышает лимит"
      ]
    }
  ],
  "relaxedCriteria": [],
  "message": null
}
```

В реальном контракте поля должны быть типизированы Pydantic-схемами. Не возвращать причины, которые не соответствуют реально выполненным проверкам.

## 10.7. Ошибки API

Согласовать единый формат ошибки:
- машинный код;
- человекочитаемое сообщение;
- необязательные детали валидации;
- request ID при необходимости.

Ожидаемые ситуации:
- `400` — некорректная операция;
- `401` — не авторизован;
- `403` — нет прав;
- `404` — фильм/запись не найдены;
- `409` — конфликт состояния, если он не обрабатывается идемпотентно;
- `422` — ошибка валидации;
- `429` — ограничение запросов, если применяется;
- `500` — непредвиденная ошибка сервера.

Frontend должен различать отсутствие результатов и ошибку сервера.

# 11. Нефункциональные требования

## 11.1. Надёжность
- ошибки загрузки не должны приводить к белому экрану;
- некорректное локальное состояние не должно ломать приложение;
- действия пользователя должны иметь loading/success/error состояния, где это необходимо;
- повторное нажатие не должно создавать дубликаты.

## 11.2. Производительность
- избегать лишних повторных запросов;
- не загружать большие списки без необходимости;
- использовать пагинацию, если каталог станет большим;
- кэшировать только после определения стратегии и необходимости.

## 11.3. Безопасность
- секреты TMDB не размещать в frontend;
- валидировать все входные данные на сервере;
- проверять доступ пользователя к его записям;
- не доверять `userId`, пришедшему от клиента;
- не возвращать приватные данные другого пользователя;
- не хранить пароли в открытом виде;
- при реализации авторизации использовать стандартные безопасные механизмы и хранить секреты в переменных окружения.

## 11.4. Адаптивность и доступность
- все функции доступны на мобильных устройствах;
- кликабельные элементы имеют понятные размеры;
- интерактивные элементы доступны с клавиатуры;
- фокус видим;
- у иконок без текста есть доступные подписи;
- эффекты не мешают чтению и навигации;
- учитывать `prefers-reduced-motion`.

## 11.5. Киноэффекты
- `PopcornEffect`, `ClapboardTransition`, `PageTransition`, `FilmEffects` — декоративный слой;
- эффекты не должны блокировать переходы и нажатия;
- при отключённой анимации основной функционал сохраняется;
- не запускать эффекты многократно из-за повторных рендеров;
- не использовать эффект для маскировки ошибок состояния;
- эффекты не важнее стабильности интерфейса.

# 12. Обработка пустых состояний и ошибок

Для каждого основного экрана предусмотреть четыре класса состояний:
1. загрузка;
2. данные доступны;
3. пустой результат;
4. ошибка.

Примеры:
- каталог пуст после фильтрации — сообщить, что совпадений нет, дать сбросить фильтры;
- библиотека пуста — предложить открыть каталог;
- избранное пусто — предложить найти фильм;
- история пуста — объяснить, что она появится после отметки просмотра;
- фильм не найден — дать переход к каталогу;
- подбор не нашёл точных совпадений — показать причины и управляемые варианты изменения критериев;
- API недоступен — показать ошибку и действие повтора, не выдавать пустой массив за успешную загрузку;
- постер не загрузился — показать локальный fallback, не ломая размеры карточки.

# 13. Дефекты, уже отмеченные в текущем аудите

Ниже — исходные гипотезы аудита, которые Copilot должен подтвердить по реальному коду и исправить. Не считать их окончательно доказанными без повторной проверки.

## Высокий приоритет

### D-01. Подбор ослабляет условия без явного согласия
Ожидаемое исправление:
- разделить жёсткие ограничения и мягкие предпочтения;
- удалить случайный fallback на неподходящий фильм;
- объяснять отсутствие результатов;
- показывать ослабленные условия;
- сбрасывать устаревший результат при изменении ответов.

### D-02. Статусы фильма расходятся между страницами
Ожидаемое исправление:
- единый источник пользовательского состояния;
- одна запись `UserMovie` на фильм пользователя;
- согласованные статусы;
- единые операции добавления, изменения, удаления;
- синхронное обновление страниц.

### D-03. Счётчики и история являются демонстрационными
Ожидаемое исправление:
- пересчитывать статистику по фактическим данным;
- отделить mock-данные каталога от персональных записей;
- не показывать фиктивные даты просмотра;
- не выдавать внешний рейтинг за личную оценку.

### D-04. Страница фильма содержит неполные/фиктивные блоки
Ожидаемое исправление:
- отображать только реальные доступные поля;
- не дублировать режиссёра в других секциях;
- не показывать фиктивный трейлер;
- не добавлять вымышленные сведения о составе съёмочной группы.

## Средний приоритет

### D-05. Диапазоны лет пересекаются или не совпадают с подписью
- привести подписи и условия к одним диапазонам;
- покрыть тестами граничные годы.

### D-06. «Популярные» не меняют порядок
- использовать реальное поле популярности или определить честное название блока/сортировки;
- покрыть сортировку тестом.

### D-07. Глобальный поиск и каталог ищут по разным полям
- общий модуль поиска;
- поиск по названию, оригинальному названию, режиссёру и жанрам;
- одинаковая нормализация запроса.

### D-08. Настройки профиля не влияют на поведение
- подключить каждую настройку к реальному состоянию и хранению либо убрать/обозначить её как недоступную.

## Низкий приоритет

### D-09. Неиспользуемые заглушки и дублирующиеся сервисы
- проверить usage/imports;
- не удалять без анализа;
- определить один путь сохранения состояния;
- удалить лишнее только после подтверждения отсутствия использования.

### D-10. Некорректное содержимое localStorage может ломать приложение
- безопасный parse;
- runtime-валидация структуры;
- fallback;
- тесты повреждённых/устаревших данных.

### D-11. Недостаточно автоматизированных проверок
- добавить тесты для бизнес-правил до масштабной интеграции backend;
- отдельно проверить типы, сборку, логику и ключевые пользовательские сценарии.

# 14. Стратегия тестирования

## 14.1. Unit-тесты бизнес-логики
Минимальный набор:
- добавление фильма в коллекцию не создаёт дубликат;
- изменение статуса не меняет избранное;
- удаление из коллекции не удаляет историю и избранное;
- оценка не смешивается с внешним рейтингом;
- средняя оценка игнорирует `null`;
- статистика соответствует фактическим данным;
- поиск находит фильм по жанру и режиссёру;
- фильтры лет корректны на границах;
- сортировка реально меняет порядок;
- подбор не нарушает жёсткие ограничения;
- отсутствие кандидатов не приводит к случайному fallback;
- повтор «Другой вариант» не дублирует результат при наличии альтернатив;
- повреждённое localStorage восстанавливается безопасно.

## 14.2. Интеграционные тесты
После появления backend:
- создание и чтение коллекции;
- изменение статуса;
- добавление/удаление избранного;
- установка/удаление оценки;
- создание события истории;
- проверка доступа к чужим данным;
- подбор с валидными/невалидными критериями;
- ошибки TMDB и недоступность БД.

## 14.3. Сквозные сценарии
1. Открыть каталог → найти фильм → открыть страницу.
2. Добавить фильм в коллекцию → обновить страницу → убедиться, что запись сохранилась.
3. Изменить статус на `watched` → проверить библиотеку, историю и статистику.
4. Поставить оценку → проверить карточку фильма и среднее в профиле.
5. Добавить в избранное → перейти на страницу избранного → удалить → проверить остальные состояния.
6. Запустить подбор → выбрать ограничения → получить совпадение или корректное пустое состояние.
7. Изменить ответ после результата → убедиться, что старый результат не выдаётся за актуальный.
8. Проверить мобильную навигацию и клавиатурное управление поиском.

# 15. Порядок реализации

Не выполнять всё за один запрос. Рекомендуемая последовательность:

## Этап 0. Безопасная фиксация
- проверить Git status;
- зафиксировать текущее состояние отдельным коммитом, если рабочий процесс это допускает;
- убедиться, что проект запускается;
- записать результаты `npm run typecheck` и `npm run build`;
- не изменять код в рамках самого аудита.

**Критерий готовности:** известна базовая версия, к которой можно вернуться.

## Этап 1. Проверка модели состояния
- изучить `CineVaultProvider`;
- изучить `useLibrary`, `localStorage`, типы и все места, где изменяются статусы;
- составить таблицу текущих источников истины;
- предложить минимальную миграцию к единой модели;
- только после согласования исправить дублирование.

**Критерий готовности:** библиотека, избранное, оценки и просмотр не расходятся между страницами.

## Этап 2. Исправление каталога и поиска
- общий поиск;
- диапазоны годов;
- реальная сортировка;
- пустые состояния;
- тесты граничных значений.

**Критерий готовности:** подписи фильтров соответствуют фактическим условиям, сортировка работает.

## Этап 3. Подбор
- согласовать типы параметров;
- вынести алгоритм из UI;
- реализовать жёсткую фильтрацию и мягкое ранжирование;
- реализовать объяснения;
- исправить повторные результаты;
- создать пошаговый диалог;
- покрыть алгоритм unit-тестами.

**Критерий готовности:** алгоритм не нарушает жёсткие ограничения и объясняет отсутствие результатов.

## Этап 4. Страница фильма и профиль
- убрать фиктивные пользовательские данные;
- согласовать отображение внешнего и личного рейтинга;
- подключить статистику к фактическим данным;
- определить поведение недоступных сведений;
- проверить пустые состояния.

**Критерий готовности:** UI показывает только данные, которые действительно есть в модели.

## Этап 5. Подготовка backend-контракта
- согласовать сущности и связи;
- утвердить API;
- определить авторизацию;
- определить обработку ошибок;
- только затем создать backend и миграции.

**Критерий готовности:** frontend и backend используют согласованные типы и контракты.

## Этап 6. Подключение сервера и внешнего API
- FastAPI;
- PostgreSQL;
- миграции;
- сервисы и endpoints;
- интеграция TMDB через backend;
- интеграционные тесты.

Redis добавлять только при обоснованной необходимости.

# 16. Критерии приёмки MVP

MVP можно считать функционально целостным, когда:

- все маршруты работают и неизвестные маршруты ведут на 404;
- каталог поддерживает согласованный поиск, фильтрацию и сортировку;
- страница фильма отображает доступные данные без выдуманных пользовательских значений;
- добавление в коллекцию идемпотентно;
- статусы коллекции единообразны на всех страницах;
- избранное не смешано с коллекцией;
- личная оценка отделена от внешнего рейтинга;
- статистика вычисляется из пользовательских записей;
- история содержит события, а не демонстрационные записи;
- подбор фильтрует по жёстким ограничениям;
- подбор ранжирует по явным мягким предпочтениям;
- при отсутствии результатов пользователь получает объяснение, а не случайный неподходящий фильм;
- «Другой вариант» не повторяет уже показанные результаты, пока доступны другие кандидаты;
- изменение параметров делает прежний результат неактуальным;
- приложение корректно обрабатывает пустые данные, ошибки загрузки и повреждённое локальное состояние;
- адаптивная версия сохраняет доступность основных функций;
- сборка и проверки типов проходят;
- ключевые бизнес-правила покрыты тестами.

# 17. Обязательный формат отчёта Copilot после каждого этапа

После выполнения задачи Copilot должен сообщать:

1. **Что изменено** — кратко по поведению, не только список файлов.
2. **Какие файлы затронуты** — с назначением каждого изменения.
3. **Какие бизнес-правила реализованы** — со ссылкой на раздел спецификации.
4. **Что проверено** — точные команды и фактические результаты.
5. **Какие тесты добавлены** — и что они проверяют.
6. **Что осталось нерешённым** — включая известные ограничения.
7. **Что намеренно не менялось** — особенно дизайн, API и архитектура вне текущего этапа.
8. **Есть ли расхождения со спецификацией** — не скрывать их и не принимать архитектурные решения молча.

Запрещено писать «всё проверено», если запускались только проверки TypeScript. Проверка типов, сборка, unit-тесты и ручная проверка пользовательских сценариев — разные виды проверки.
