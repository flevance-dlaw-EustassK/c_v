# CineVault — контекст и правила работы

Этот файл хранит договорённости проекта для следующих сессий Codex. Перед работой прочитай его и инструкции в `.github/copilot-instructions.md`. Проверяй актуальный код: обсуждённые планы не равны реализованным возможностям. Прямые указания пользователя имеют приоритет; при изменении решений актуализируй этот файл.

## Назначение и ВКР

Тема со слов автора: «Информационная система по персонализированному подбору фильмотеки для домашнего кинотеатра». Точное официальное написание сверять с утверждённым заданием.

CineVault объединяет исследование кино, личную фильмотеку и подбор фильма под предпочтения пользователя и ситуацию просмотра. Это не онлайн-кинотеатр: воспроизведение фильмов не входит в текущий объём.

Проект выполняет один студент для ВКР в МГТУ им. Н. Э. Баумана, кафедра ИУ-5. Руководитель — Постников Виталий Михайлович. Плановый срок защиты по предоставленному контексту — май 2027 года. Объём должен быть реалистичным, а решения — объяснимыми на защите.

Работа включает не только код, но и описание предметной области, анализ аналогов, требования, схемы процессов и архитектуры, модели данных, описание алгоритма, тестирование, пояснительную записку и презентацию. Форматы диаграмм и оформление согласовывать с методичкой кафедры. Схемы, текст и реализация должны соответствовать друг другу. Отличать текущее состояние от проектируемого.

## Подтверждённый технический контекст

- React, TypeScript, Vite, React Router, CSS Modules, npm.
- Страницы в `src/pages`, общие компоненты в `src/components`, типы в `src/types`, локальные данные в `src/data`, хранение и API-логика в `src/services`.
- Проверенная исходная версия: `afa0b09` в `feature/user-state-model`. Она использует моковые сведения о кино, React Context и localStorage. Есть каталог, страницы фильмов/персон/студий/событий, подбор, фильмотека, избранное и профиль.
- Сообщение из другой сессии о пятишаговом подборе и 16 тестах не подтверждает наличие этих изменений в текущем checkout. Всегда проверяй файлы и команды.
- Сейчас разрабатываем frontend-прототип. Backend, реальную авторизацию и внешние API без отдельной задачи не подключать. FastAPI, PostgreSQL, Redis и Docker обсуждались как будущие варианты, а не готовые компоненты.
- Изображения TMDB CDN не означают интеграцию с TMDB API. Для отсутствующих изображений нужны локальные заглушки.

## Продуктовые требования

- Основной путь: знакомство со вкусами → исследование → сохранение → выбор на вечер → просмотр и оценка → уточнение рекомендаций.
- Каталог и связанные сущности помогают формировать личную фильмотеку. Не сводить продукт только к набору карточек.
- Различать планы, просмотренное, избранное, оценки, события просмотров и пользовательские подборки. Действия согласованно работают на разных страницах и сохраняются после перезагрузки.
- Статистика рассчитывается из пользовательских данных. Демонстрационные действия не выдавать за реальные; новый пользователь не должен незаметно получать выдуманную историю.
- Персонализация использует долгосрочные предпочтения отдельно от контекста конкретного вечера. Отказ «не сегодня» не равен постоянной отрицательной оценке.
- Жёсткие ограничения применять до ранжирования и не ослаблять молча. При отсутствии результатов объяснять ситуацию и предлагать явное изменение условий.
- Рекомендации объяснять реально сработавшими факторами. Не заявлять сложный ИИ, научную новизну или проценты совпадения без основания.
- Не обещать семейную безопасность, доступность стриминга и другие свойства, для которых нет достоверных данных.
- Сохранять фильтры и положение каталога при возврате; унифицировать поиск и пользовательские действия; предусматривать пустые состояния и ошибки.

## Направление улучшений

Предложенная концепция, а не утверждение о готовности: короткий подбор на вечер с изменяемыми ответами; один основной результат и альтернативы; необязательное знакомство со вкусами; главная с планами и объяснимыми рекомендациями; подбор из личных планов; удобные подборки; явная регистрация повторного просмотра; URL-фильтры и поиск по типам сущностей.

Спорные продуктовые решения обсуждать с автором. Идея или аудит сами по себе не являются поручением менять код. При явной задаче реализации выполнять работу до проверяемого результата.

## Дизайн и качество

- Сохранять тёмную кинематографичную/editorial-эстетику: чёрно-коричневый фон, бордовый акцент, Inter, выразительная типографика и ряды постеров.
- Не превращать сайт в типовой dashboard. Не менять весь дизайн без согласования.
- Одно главное действие на смысловой блок, единые элементы управления, понятная навигация, адаптивность, доступная клавиатура и видимый фокус.
- Анимации вторичны; учитывать reduced motion. Не добавлять фальшивые кнопки, искусственные задержки и декоративные показатели.
- Не добавлять социальную сеть, комментарии, подписки, достижения и подбор по музыке.
- Не вводить Tailwind, Redux, Zustand, новые библиотеки или архитектурные слои без реальной необходимости. Переиспользовать существующие решения.
- Сохранять пользовательские данные; изменения схемы localStorage сопровождать валидацией и миграцией.

## Материалы ВКР

- Проверять возможности аналогов по источникам и фиксировать дату, тариф и ограничения исследования.
- Авторские веса и баллы честно обозначать экспертными; не выдавать их за результаты опроса.
- Не доказывать превосходство прототипа оценками планируемых функций. Разделять реализованные и проектируемые возможности.
- Алгоритм описывать через входы, ограничения, ранжирование, объяснения, поведение при пустой выдаче и проверочные сценарии.
- Не проектировать окончательную БД до фиксации функций. Не выдумывать экспериментальные результаты и не считать непроверенные замечания старого аудита актуальными.

## Сотрудничество и Git

Общаемся по-русски, конкретно, без лишних объяснений. Пользователь ожидает и продуктовые предложения, и реализацию, и помощь с ВКР.

Рабочий порядок: одна задача → отдельная ветка → проверенные коммиты → push → Pull Request → проверка пользователем → merge пользователем. Создание ветки, коммитов и PR — обычная часть явно порученной задачи в этом облачном чате. Не сливать PR и не развёртывать сайт без указания.

- На момент сохранения основная рабочая ветка с приложением — `feature/user-state-model`. Не предполагать, что `main` содержит актуальный сайт. Перед задачей проверять удалённые ветки и состояние; переход на `main` отдельно согласовать.
- Ветки: `feat/<задача>`, `fix/<задача>`, `docs/<задача>`. Исправления по PR добавлять в ту же ветку.
- Использовать существующий изолированный checkout; Git worktree не создавать без явной просьбы.
- Не включать чужие изменения, не использовать разрушительные reset/force push. Проверять статус до и после работы.
- Облачный checkout не является папкой пользователя на компьютере. Коммит не виден в GitHub до успешного push. PR не является предпросмотром сайта.
- Пользователь проверяет ветку локально до merge. Давать ссылку PR и точные команды `git fetch`, переключения ветки, установки при необходимости и запуска. Не предлагать удалять локальные изменения при конфликте.
- При локальной работе Codex в VS Code учитывать инструкции текущей сессии: не предполагать разрешение на push из одного факта редактирования.

## Проверка и отчёт

Перед запуском проверять актуальный `package.json`. В исходной версии: `npm ci`, `npm run dev`, `npm run typecheck`, `npm run build`. Тестовую команду использовать, только если она действительно существует. Для README и других простых правок не запускать ненужную сборку; достаточно проверки diff.

Для логики подбора и состояния нужны содержательные проверки, для UI — соответствующие функциональные сценарии и адаптивность. Не считать успешную сборку доказательством корректности рекомендаций.

В конце сообщать: что изменено, что фактически проверено, ограничения, ветку и ссылку PR. Чётко различать локальный коммит, push, открытый PR, merge и публикацию.
